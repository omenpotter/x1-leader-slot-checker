X1 leader schedule explained

By ARKBS Labs · Updated 20 November 2026 · Figures verified against X1 Mainnet RPC on that date

In short: X1 Mainnet divides time into slots and groups them into 216,000-slot epochs. Before each epoch, a stake-weighted schedule assigns every slot to a validator identity, in runs of four. A validator's "leader slots" are its turns to produce blocks. You can read the schedule from any X1 RPC node with getLeaderSchedule; converting slot numbers to clock times is always an estimate.

1. Slots and slot timing on X1

A slot is the window in which one designated validator — the leader — may produce a block. X1's documentation describes slots as fixed at 400 milliseconds, inherited from the Solana design. In practice the observed average is set by the network: on 20 November 2026, getRecentPerformanceSamples on X1 Mainnet reported about 164 slots per 60-second sample, roughly 365 ms per slot.

That difference matters for anyone estimating timing: a projection 100,000 slots ahead differs by more than an hour between 365 ms and 400 ms. The checker therefore measures slot time from recent samples instead of assuming 400 ms.

2. Epochs on X1 Mainnet

An epoch is a fixed range of slots for which one leader schedule and one stake snapshot apply. getEpochSchedule on X1 Mainnet returns:

FieldX1 Mainnet valueMeaning
slotsPerEpoch216,000Slots in every normal epoch
leaderScheduleSlotOffset216,000The schedule is known one epoch ahead
warmuptrueEarly epochs were shorter, doubling in length
firstNormalEpoch13First full-length epoch
firstNormalSlot262,112First slot of epoch 13

For any epoch E ≥ 13, the first slot is 262,112 + (E − 13) × 216,000. Epoch 449, for example, starts at slot 94,438,112 — matching the range reported by getBlockProduction. At ~365 ms per slot an X1 epoch lasts about 22 hours (24 hours at 400 ms). Solana Mainnet epochs are twice as long (432,000 slots, roughly two days), so Solana rules of thumb do not carry over.

3. How leaders are selected

The leader schedule is derived from the stake distribution: each validator's chance of being chosen for a slot is proportional to its activated stake, and a deterministic pseudo-random seed fixes the order so every node computes the same schedule. More stake means more leader slots, not specific slots.

X1's documentation notes that stake weight is currently the only selection criterion and lists performance- and randomness-based leader selection on its technical roadmap. That is a roadmap item; this guide describes the network as it behaves today.

4. Leader windows

Leaders are scheduled in runs of four consecutive slots. In the recorded schedule for one X1 validator, every assignment appeared as a run such as 2232, 2233, 2234, 2235 (epoch-relative). The checker groups these runs into "leader windows" so a schedule of 236 slots reads as 59 windows.

5. Verify a schedule with RPC

Everything the checker shows can be reproduced with public JSON-RPC calls against https://rpc.mainnet.x1.xyz. Request only the identity you need — the unfiltered schedule for all validators is about 1.4 MB.

curl https://rpc.mainnet.x1.xyz -s -X POST -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 1, "method": "getLeaderSchedule",
  "params": [null, { "identity": "<VALIDATOR_IDENTITY>" }]
}'

The result maps the identity to epoch-relative slot indices. Add the epoch's first slot to get absolute slot numbers. To read the next epoch, pass any slot inside it as the first parameter; nodes return null for epochs whose schedule is not yet computable.

If you only have a vote account, call getVoteAccounts with {"votePubkey": "…"} and use the returned nodePubkey. Mind the public RPC rate limits (per IP: 300 requests per 5 seconds, 150,000 per hour).

6. From slot numbers to clock time

The schedule is defined in slots, not seconds. To estimate when slot S begins:

  1. Observe the current slot C at a known time t.
  2. Measure average slot duration d from recent performance samples.
  3. Estimate start ≈ t + (S − C) × d.

The checker also computes the estimate with the fastest and slowest recent one-minute samples to show a range, and recalibrates against the live slot every 20 seconds. Uncertainty grows with distance: a slot an hour away is far more predictable than one twenty hours away.

7. Scheduled versus produced blocks

A leader slot is an opportunity, not a guarantee. If the leader is offline, delinquent, out of sync or its block does not reach the cluster, the slot is skipped. getBlockProduction returns, per identity, the leader slots elapsed so far this epoch and the blocks actually produced; the difference is the skip count. X1 Space and the checker both show these figures, and elapsed windows in the checker link to the block page on X1 Space.

8. X1, the SVM and Solana compatibility

X1 is a high-performance layer-1 that is fully compatible with the Solana Virtual Machine (SVM); its RPC currently reports a Solana-compatible validator client (solana-core 4.0.4). That compatibility is why standard tools — the solana CLI, wallets and the JSON-RPC methods above — work against X1. X1 changes several economic and network parameters relative to Solana, including zero-cost validator votes and congestion-reflective dynamic base fees, and its epoch length and observed slot timing differ as described above.
